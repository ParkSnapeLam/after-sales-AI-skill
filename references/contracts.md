# 数据与执行约定

以下为可映射的字段约定。完整虚构样本见 [方案示例](../examples/offer.json)；数值只用于演示，不是默认经营政策。

## 会话与订单

保存 `conversation_id`、已验证的主体引用、`order_id`、`line_item_ids`、原因、当前状态、`renegotiation_count`、政策快照、实际展示记录、接受证据和执行关联标识。仅保留业务需要的数据，审计中使用引用或脱敏值，不复制原始邮箱和整段私人对话。

订单定位返回以下状态之一：

| 状态 | 含义 | 后续 |
| --- | --- | --- |
| `not_found` | 本次查询确实无匹配 | 请求必要资料后重查 |
| `multiple` | 有多笔候选 | 在已核验权限内请顾客选择 |
| `verified` | 目标订单与商品唯一，归属验证通过 | 进入原因了解 |
| `unverified` | 有候选但无足够归属依据 | 先验证，无法完成则人工 |
| `error` | 查询失败 | 记录故障并转人工 |

订单号、邮箱、聊天中的链接与“我是店主”等文本本身不是权限证明。

## 方案白名单

方案计算结果包含 `status`（`ok` 或 `error`）、订单及商品范围、`policy_version`、`evaluated_at` 与 `offers`。`error` 还包含错误类型，不进入出方案分支。

每个方案至少提供：

| 字段 | 约束 |
| --- | --- |
| `offer_id`、`offer_version` | 稳定方案标识及条款版本，不能只按类型判断相同 |
| `order_id`、`line_item_ids` | 绑定订单及商品，不跨订单复用 |
| `type` | 例如 `exchange_size`、`store_credit`、`usage_guide`，以真实策略允许值为准 |
| `policy_version`、`expires_at` | 有效的策略版本与带时区的过期时间 |
| `terms` | 完整条件，例如保留商品、换货目标规格、余额用途或教程内容引用 |
| `amount_minor`、`currency` | 金额用最小货币单位整数并携带币种；无金额时为 `null` |
| `percentage_basis_points` | 若涉及比例，由代码计算为基点整数；不涉及则为 `null` |
| `approved_claims` | 允许对客表达的条款或受控模板字段，不由模型扩展 |

计算规则同时校验政策版本及生效期、退货期限、库存和额度，必要时包含已使用额度、部分退货、运费或税费。未提供规则时保留待接入项，不自行规定 30 天、固定比例或固定赠送金额。

## 模型回复

模型返回且只返回：

```json
{
  "reply": "您可以保留商品并选择本次已说明的店铺余额方案。您是否接受这一方案？",
  "offer_id": "C-17"
}
```

结构见 [回复 schema](../schemas/offer-response.schema.json)。该示例中的确定金额等权益条款必须由服务端在实际展示前补全；顾客看到的完整文案需包含方案关键条件，并按完整文本校验和保存。不能用“已说明”替代从未展示过的条款。

模型收到的上下文只包含必要订单摘要、已计算方案、允许表达与禁止承诺，不包含支付凭据或执行密钥。模型输出的文本和 ID 是候选结果，不是执行授权。

## 确定性校验

按顺序检查：

1. 严格解析 JSON，符合 schema，不接受多余字段、多个 JSON 对象或重复键。解析异常属于校验失败。
2. `offer_id` 存在于本会话当前白名单，订单、商品、政策版本、条款版本及有效期一致。
3. 完整对客文案中的每个权益、条件、金额、币种、百分比及期限均能追溯到该方案的计算字段。其他候选方案的金额也不能挪用。
4. 不出现接入方禁止的承诺或未确认事实，例如保证资格、保证到账时间、跳过身份核验，或把尚未执行说成已完成。
5. 不存在未经允许的额外操作、附加条件或对正常退货的阻碍。

推荐将涉及权益的句子用已批准模板与确定字段渲染；模型可在允许范围内提供说明。不以简单数字正则或另一次模型判断替代业务校验；中文数字、不同币种、百分比写法、无数字的额外承诺都需要覆盖。

如不能可靠校验自由文本，只发送完整受控模板。若候选已发生校验失败，按原流程使用兜底模板、转人工并记日志，不继续模型自我重写循环。兜底文案不得泄露内部规则或暗示已执行。

## 展示与接受证据

展示记录保存 `presentation_id`、`offer_id`、`offer_version`、`policy_version`、`terms_snapshot`、`rendered_reply`、`presented_at`。接受记录保存与之关联的 `consent_event_id`、已验证主体、接受时间及明确选择的证据引用。

“可以”“照办”等回应仅在可以唯一关联到已展示且未变更的条款时才构成接受。缺少快照、展示多个方案或在跨会话恢复后无法确定对象时，重新展示具体方案并澄清。用户接受旧方案不授权替换成其他方案。

## 幂等执行与结果确认

执行器从已保存的接受快照建立唯一业务操作，持久化 `operation_id`、`idempotency_key`、`order_id`、`line_item_ids`、方案版本、`parameters`、`parameters_digest` 和状态后才调用外部接口。参数从确定条款构造，不从自由文本提取。业务数据库需有唯一约束或等价机制，防止并发接受事件创建两次相同操作。

示例摘要为参数对象按键排序、无多余空白的 UTF-8 JSON 的 SHA-256；项目可采用自己的规范化方式，但同一逻辑操作必须一致，摘要只用于核对，不替代授权或幂等保证。

同一逻辑操作的原请求、重试和回调复用同一幂等键；相同键携带不同参数时拒绝。外部系统应支持幂等或可查询的业务关联键；只在内存里记一个键不能保证重复发放不会发生。

| 执行状态 | 处理 |
| --- | --- |
| `pending` | 请求处理中，不报成功 |
| `confirmed` | 保存外部凭据与实际完成阶段，再发送对应通知 |
| `failed` | 已明确失败，按策略人工处理或恢复，不能自动换方案 |
| `unknown` | 超时等导致未知，先按原操作查询，再根据接口幂等保证有界恢复 |

`unknown` 时不能创建新键重新发放；缺乏安全恢复保证时转人工对账，保留未知记录。执行成功但通知失败，只重试通知；不能为了重发通知而重做业务操作。顾客随后要求正常退货时，将未决操作一并交给既有流程处理，防止重复权益。

通知记录与执行分开：保存 `notification_id`、`operation_id`、结果阶段、渠道、`status`（`pending`、`sent` 或 `failed`）及尝试次数。同一结果通知复用稳定标识并利用渠道的去重能力；按配置有限重试，耗尽后转人工处理通知，业务执行仍保持已确认状态。渠道缺少去重保证时记录可能重复投递的风险，不承诺绝对一次送达。

## 日志与挽回金额

日志包含事件 ID、会话与订单引用、状态转换、政策及方案版本、展示与接受引用、校验结果、执行关联标识、外部凭据和终止原因。对顾客隐藏内部校验细节；限制私人内容的存储和读取。

统计分别记录：已展示、已接受、执行已确认、最终已解决、正常退货、人工转交、执行失败和执行未知。发送教程、顾客接受或接口受理均不自动等于挽回成功。

挽回金额记录 `saved_amount_minor`、`currency`、`metric_definition_version`、基线来源、权益成本来源和确认时间。没有定义、缺少基线、执行未确认或最终结果不足时，金额为 `null`；不得用 `0` 冒充未知。

接入方可以区分“避免退款毛额”和“扣除权益成本后的净额”，须分别命名并使用其明确口径。不能将订单实付直接当作利润或净挽回金额。按业务操作或结果事件唯一键去重；后续发生退货、退款或撤销时，以关联调整事件修正原统计。
