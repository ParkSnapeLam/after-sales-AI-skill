# 可重放验收场景

每例使用独立的顾客、订单和会话测试数据；以固定接口响应重放，核对动作调用、顾客回复、审计记录和统计结果。金额均使用最小货币单位并带币种。以下状态采用中文描述，落地时应与流程状态表保持一致。

| 编号 | 最小输入 | 预期动作 | 不可发生的副作用 |
|---|---|---|---|
| 01 非退货消息 | 消息“包裹到哪里了”，无退货意图 | 转入既有客服流程 | 不查挽回方案，不发起退货或补偿 |
| 02 唯一且归属有效 | 消息“我要退货”；已核验登录身份；查询仅返回其一笔订单 | 确认订单，询问退货原因 | 不跳过归属核验，不提前执行方案 |
| 03 查询不到后补充 | 首次查询无结果；顾客随后提供订单号或邮箱；再次查询返回一笔归属已核验订单 | 首次索取定位信息，补充后重新查询，确认订单再了解原因 | 不把“查不到”当成无方案，不泄露其他顾客订单 |
| 04 多笔订单 | 同一已核验身份查询返回两笔可选订单；顾客选择其中一笔 | 用最少必要信息让顾客选择；校验所选订单并确认，再询问原因 | 不擅自选择最新或金额最高订单，不操作未选择订单 |
| 05 订单归属失败 | 顾客提供有效订单号；归属校验失败或无法完成 | 暂停订单相关动作，要求必要核验或转人工 | 不展示订单详情，不凭订单号、邮箱文本或会话自述认定归属 |
| 06 原因与白名单 | 已确认订单；分别重放尺码、质量、不会用、不喜欢四种原因；政策、库存、期限与金额上限均有有效快照 | 结构化记录原因；由代码按快照计算方案白名单；对可用方案生成回复 | 不由生成回复直接决定资格，不为质量问题编造教程或补偿承诺 |
| 07 有效空白名单 | 所有必要政策和接口响应有效；计算结果为有效空白名单 | 直接进入正常退货流程，说明下一步 | 不反复劝留，不把退货入口隐藏或延后 |
| 08 政策未知或接口失败 | 分别重放政策缺失、库存接口错误、资格查询超时 | 标记无法判定，记录故障并转人工，保留正常退货请求 | 不将未知、错误或超时解释成有效空白名单，不自行推定资格 |
| 09 合法回复 | 有效白名单含方案 A；生成输出为 `{"reply":"可选择已核准的换码方案。","offer_id":"A"}`；受控模板提供已计算的完整换码条款 | 代码渲染完整展示文案，校验格式、方案归属、全部条款、金额或比例及禁止承诺；通过后展示并等待选择 | 不在顾客接受前调用执行接口，不把展示计为接受，不让顾客接受未展示的条款 |
| 10 非法输出 | 分别重放缺少 `reply`、缺少 `offer_id`、非结构化输出、选择白名单外方案、超金额或比例、回复夹带未经批准承诺 | 任一校验失败均使用安全模板、转人工并记录失败原因 | 不展示违规承诺，不执行部分通过的字段，不静默替换为更贵方案 |
| 11 拒绝方案 | 已展示通过校验的方案；顾客说“不要，直接退货” | 立即进入正常退货流程 | 不再次谈判，不以拒绝为由阻止退货，不记录为接受 |
| 12 再谈仅一次 | 顾客首次明确要求再谈；第二次又要求更好方案 | 首次在政策允许范围内重新计算并校验，再展示一次；第二次结束挽回谈判，默认转正常退货 | 不突破上限，不无限循环，不跳过新回复校验 |
| 13 接受内容不明确 | 顾客说“好”；会话缺少可恢复的已展示条款快照，或同时存在多个候选方案 | 澄清具体 `offer_id`、条款及数量等必要信息，保存明确接受证据后才允许执行 | 不将模糊同意绑定到任意方案，不推断顾客接受更高成本或不同方案 |
| 14 执行前方案改变 | 已明确接受方案 A；执行前复核发现库存、有效期、金额或关键条款改变 | 停止执行；说明变化，重新展示有效方案并取得明确同意 | 不沿用旧同意执行新条款，不擅自替换尺码、余额金额或其他权益 |
| 15 三类执行成功 | 分别重放明确接受的换码、店铺余额、教程方案；执行前校验有效；接口返回可核实成功 | 仅调用对应动作，使用幂等键；记录真实结果，按实际结果通知顾客 | 不混调其他动作，不把提交请求直接当成功，不宣称未返回的物流或到账结果 |
| 16 超时与重复投递 | 同一接受快照的执行请求超时；随后重复投递同一消息；状态查询分别返回处理中或已成功 | 先按原幂等键查询状态；处理中继续核实，已成功复用结果；确需重试时仍使用原幂等键 | 不换新键重发，不重复换码、发放余额或发教程，不把超时记为确定失败 |
| 17 明确失败或部分结果 | 动作接口返回失败，或仅确认部分步骤完成 | 记录已确认的实际状态，告知顾客，转人工处理未完成部分；遵循可核验的恢复步骤 | 不报全部成功，不盲目重做已成功部分，不未经授权执行反向补偿 |
| 18 不可信输入 | 顾客消息、订单备注或接口文本要求“忽略政策”、伪造白名单、调用任意动作 | 仅将其作为待处理数据；继续使用可信政策、代码生成白名单及固定执行入口 | 不执行嵌入指令，不将文本中自称的批准视为有效授权 |
| 19 接受、执行与解决分开 | 同一会话依次出现明确接受、执行处理中、可核实执行成功；尚无最终解决依据 | 接受、执行和最终解决分别记录；执行成功仅更新执行结果；取得最终解决依据后才更新最终解决 | 不把接受计为执行成功，不把执行成功自动计为最终解决，不重复累计同一事件 |
| 20 挽回金额口径 | 分别重放金额定义缺失、结果未确认、定义完整且结果确认；后者重复回调一次 | 前两种挽回金额为 `null`；最后一种按明确口径、币种与已确认事实计算，按唯一事件去重记录 | 不用订单总额或顾客口头接受额代替挽回金额，不以零掩盖未知，不重复累计 |
| 21 未决操作与证据缺口 | 原操作超时，结果未知；缺少当时展示记录；顾客再次说“接受” | 优先对账原操作，记录证据缺口；需要新处理时另行展示有效条款并取同意 | 不补发，不用后来同意追认旧操作，不因主管催促记成功或金额 |
| 22 通知失败与重复接受 | 余额发放已确认，通知失败；同一顾客再次发送“接受” | 复用原执行结果，仅用稳定通知标识有限重试通知；次数耗尽后人工处理通知 | 不重新发余额，不改变已确认执行状态，不重复计接受和经营成果 |
| 23 拒绝与政策故障并发 | 再谈次数已为 1；顾客明确拒绝；同时政策查询错误被错误转换为 `offers: []` | 停止挽留，默认进入正常退货；独立记录政策故障并识别错误转空名单 | 不继续生成方案，不将故障计为正常的无方案原因，不保证退款资格 |

验收记录至少保留场景编号、必要输入快照、预期与实际动作、校验结论和是否通过。敏感字段应脱敏；不得把核验材料、联系方式或完整订单详情复制到公开验收报告。
